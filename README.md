# Jordan JoFotara × POS — an integration guide for developers and owners

> Maintained by the team that builds [RAWA](https://rawaerp.com), a Jordanian restaurant POS that implements
> everything below in production. This guide describes what we learned and what our own code does; it is not
> an official ISTD document. **Always verify against the current official JoFotara documentation.**

JoFotara (جو فوترة) is Jordan's national e-invoicing system run by the Income and Sales Tax Department (ISTD,
دائرة ضريبة الدخل والمبيعات). A POS that issues tax invoices must report each one to it. This page covers the
moving parts a POS integrator has to get right.

## 1. What you need before writing code

| Item | Notes |
|---|---|
| Taxpayer registration | The business is registered with ISTD and enrolled in JoFotara. |
| Tax number (TIN) | Goes in the supplier party (`PartyTaxScheme/CompanyID`). |
| API credentials | A **Client ID** and a **Secret Key** issued from the JoFotara portal. They travel as the HTTP headers `Client-Id` and `Secret-Key`. Treat the key like a password: store it encrypted, never in the repository, never in logs. |
| Income-source sequence | The activity/income-source sequence number from the taxpayer's registration; it is sent in the `SellerSupplierParty` block. |
| Invoice category | *Income*, *general sales* or *special sales*, each in a cash and a receivable (credit) flavour — see the `name` attribute in §3. |

## 2. The request

One HTTPS `POST` per invoice. The XML document is **base64-encoded** and wrapped in a small JSON body:

```http
POST https://backend.jofotara.gov.jo/core/invoices/
Content-Type: application/json
Client-Id: <your client id>
Secret-Key: <your secret key>

{"invoice": "<base64 of the UTF-8 UBL XML>"}
```

A runnable minimal example is in [`examples/submit_invoice.py`](examples/submit_invoice.py).

## 3. The invoice document (UBL 2.1)

The document is a UBL 2.1 `Invoice` with `ProfileID` `reporting:1.0`. The elements that matter, in order:

```xml
<Invoice xmlns="urn:oasis:names:specification:ubl:schema:xsd:Invoice-2"
         xmlns:cac="urn:oasis:names:specification:ubl:schema:xsd:CommonAggregateComponents-2"
         xmlns:cbc="urn:oasis:names:specification:ubl:schema:xsd:CommonBasicComponents-2">
  <cbc:ProfileID>reporting:1.0</cbc:ProfileID>
  <cbc:ID>INV-0001</cbc:ID>                      <!-- your invoice number -->
  <cbc:UUID>7c1f...-uuid4</cbc:UUID>             <!-- generated by YOU, once per invoice -->
  <cbc:IssueDate>2026-11-09</cbc:IssueDate>
  <cbc:InvoiceTypeCode name="012">388</cbc:InvoiceTypeCode>   <!-- 388 invoice / 381 credit note -->
  <cbc:DocumentCurrencyCode>JOD</cbc:DocumentCurrencyCode>
  <cbc:TaxCurrencyCode>JOD</cbc:TaxCurrencyCode>
  <cac:AdditionalDocumentReference>              <!-- invoice counter value (ICV) -->
    <cbc:ID>ICV</cbc:ID><cbc:UUID>57</cbc:UUID>
  </cac:AdditionalDocumentReference>
  <cac:AccountingSupplierParty>…TIN + registered name + country JO…</cac:AccountingSupplierParty>
  <cac:AccountingCustomerParty>…optional customer…</cac:AccountingCustomerParty>
  <cac:SellerSupplierParty>…income-source sequence…</cac:SellerSupplierParty>
  <cac:AllowanceCharge>…invoice-level discount…</cac:AllowanceCharge>
  <cac:TaxTotal>…</cac:TaxTotal>
  <cac:LegalMonetaryTotal>…tax-exclusive, tax-inclusive, allowance, payable…</cac:LegalMonetaryTotal>
  <cac:InvoiceLine>…one per item; a separate line for a service charge…</cac:InvoiceLine>
</Invoice>
```

**`InvoiceTypeCode/@name`** encodes category × payment kind. The mapping we use:

| Category | Cash | Receivable (credit) |
|---|---|---|
| Income | `011` | `021` |
| General sales | `012` | `022` |
| Special sales | `013` | `023` |

A sale is "cash" when nothing is outstanding on it; otherwise it is "receivable".

**Tax category.** Standard-rated sales use category `S` with the tax percentage (e.g. `16.000`); invoices
with no tax use category `O`. Amounts are decimals with three digits (`_amt()` in our code → `"%.3f"`).

## 4. Reading the response

Successful responses carry the QR code string and the invoice UUID; the key names vary by response shape,
so read defensively:

- QR: `QR_CODE`, or `EINV_QR`, or nested under `EINV_RESULTS`.
- UUID: `EINV_INV_UUID`.
- Rejections: `EINV_RESULTS.ERRORS` is a list of `{EINV_CODE, EINV_MESSAGE}` — **surface the first message to
  the user**. Showing a bare "ERROR" makes failures impossible to diagnose.

Treat an invoice as *cleared* only when HTTP is 200/201 **and** you received a QR or UUID. Print the QR on the
receipt.

## 5. Reliability: what happens when JoFotara is slow or down

A cashier must never wait on a government API. The design that has worked for us:

1. **Instant attempt with a tiny budget** (3 s) right after the sale is saved. Success → print the QR.
2. **Background queue with retries** for anything that did not clear. The sale itself is already saved and
   printed; the invoice reaches JoFotara a little later.
3. **Idempotency by UUID.** Generate the invoice UUID once, store it, and **reuse it on every retry** — a
   retry after a timeout must not create a second invoice.
4. **A shared circuit breaker.** After three network failures in two minutes, stop trying the instant path
   for 60 s so every cashier is not individually stuck waiting out a timeout while the service is down. The
   background queue keeps retrying regardless.
5. **Pooled keep-alive connections.** A fresh TCP+TLS handshake per sale is a visible cost; reuse a session.
6. **Offline POS:** if the terminal itself has no internet, queue the invoice locally and submit when the
   connection returns, in order (the ICV counter must stay monotonic).

## 6. Credit notes (returns)

A return is a **credit note**: `InvoiceTypeCode` `381` instead of `388`, positive (absolute) amounts, and a
`BillingReference/InvoiceDocumentReference` pointing at the **original invoice's id, UUID and amount**. You need
the original's UUID — one more reason to store it.

## 7. Pitfalls we hit

- **The ICV counter** must increase for every document (invoice and credit note) of a taxpayer; keep it in the
  database inside the same transaction that allocates the number.
- **Arabic names** are fine, but the document must be UTF-8 and XML-escaped (`& < > " '`).
- **Rounding:** compute per-line and totals from the same rounded values, or the totals will not reconcile.
- **Discounts** belong in `AllowanceCharge`; sending them as negative lines is rejected or mis-totalled.
- **Service charge** is its own `InvoiceLine` with its own tax block.
- **Credentials per taxpayer.** In a multi-tenant system each business has its own Client ID/Secret Key; never
  share one set across customers, and never log the secret.
- **Test credentials vs production:** keep a visible *demo* mode that never calls the API, so staff can
  practise without creating real invoices.

## 8. Test checklist

- [ ] Cash sale with tax → cleared, QR printed.
- [ ] Credit (receivable) sale to a customer with a TIN.
- [ ] Sale with an invoice-level discount.
- [ ] Sale with a service charge.
- [ ] Return → credit note references the original.
- [ ] JoFotara unreachable → cashier is not blocked, invoice is queued, no duplicate after recovery.
- [ ] Rejected invoice → readable reason shown to the operator, resubmission after correction works.
- [ ] Two terminals selling at once → ICV stays strictly increasing, no gaps caused by your own code.
